# 卡片设计审查

新增卡片或逐卡重构现有卡片时，先完成本审查，再改 Params、UI 和文档。目标不是把脚本参数原样搬进界面，而是让用户能理解、能预测、少犯错。

## 1. 先写清用户任务

用一句话写出：

> 对什么输入，执行什么物理或数据操作，得到什么输出，通常接到哪一步。

再回答：

- 这张卡解决哪个真实训练集问题？
- 输入必须满足什么前提：晶胞、PBC、元素、磁矩、层或分子拓扑？
- 输出是一帧、多帧、过滤后的子集，还是只增加标签？
- 它不负责什么：结构识别、弛豫、能量判断、代表性采样等？
- 用户如何判断结果合理？

如果一句话需要多个互不相关的动词，优先拆卡。若功能只是已有卡片的参数预设，不新建重复卡片。

## 2. 检查功能边界与重复

修改前列出同组和上下游相邻卡片，比较：

| 项目 | 当前卡片 | 相邻卡片 |
|---|---|---|
| 输入前提 |  |  |
| 核心操作 |  |  |
| 输出语义 |  |  |
| 关键参数 |  |  |
| 典型下一步 |  |  |

按以下规则判断：

- 核心输出语义相同、只差一套默认参数：合并为预设，不复制功能。
- 一个卡片同时做生成、过滤和标签：拆成可组合的卡片，除非三者是不可分割的原子操作。
- 参数只是内部算法旋钮、用户无法根据材料问题选择：不要暴露；给稳定策略或自动推导。
- 高级模式改变了输出物理含义：不要藏在折叠区里，应使用明确模式或独立卡片。

## 3. 逐项审查参数

为每个 Params 字段填写：

| 项目 | 必答问题 |
|---|---|
| 用户问题 | 用户为了什么结果会改它？ |
| 可见效果 | 它具体改变数量、组成、坐标、cell、PBC、标签还是筛选集合？ |
| 名称 | UI 文案是否描述用户动作，而不是代码实现？ |
| 类型/控件 | 数值、枚举、开关、字符串或结构化规则是否选对控件？ |
| 单位 | 单位、归一化方式和参考尺度是否明确？ |
| 参考系 | 笛卡尔、晶格分数、晶轴、Miller 指数、层法向或局部坐标？ |
| 默认值 | 对常见场景是否安全且能产生有意义结果？ |
| 范围/精度 | 上下界、步长、小数位是否符合物理量级？ |
| 禁用语义 | `0`、`None`、空字符串或单独开关分别表示什么？ |
| 联动 | 哪些模式下生效；无效时是否隐藏或禁用？ |
| 持久化 | 新旧 JSON 如何恢复；缺字段使用什么默认值？ |

必须满足：

- 每个可见参数都进入运行逻辑，并有一条断言证明效果。
- 每个影响结果的硬编码量，要么成为参数，要么在文档说明为什么固定。
- 不用同一个数字同时表达物理零值和“禁用”。只有当零没有独立物理含义时，才允许 `0 = 禁用`；否则使用明确开关。
- `min/max`、自动/手动、模式/子参数必须列真值表，检查每种组合是否生效、报错或隐藏。
- 控件允许的值必须是 operation 真正支持的值；不要依赖运行后才发现输入无效。

### 方向与轴

只有操作确实具有方向自由度时才让用户选轴。出现 `axis`、`direction`、`plane`、`normal`、`hkl` 或 `uvw` 时，必须说明：

- `x/y/z` 是笛卡尔方向，还是 `a/b/c` 晶格矢量；
- 对非正交晶胞，选择的是整根晶格矢量还是某个矩阵分量；
- 表面、层错和分层操作依据层法向、Miller 面还是当前盒子方向；
- PBC 边界处如何切分、平移和 wrap；
- 任意取向是否真的支持。若算法支持一般晶胞，不要把 UI 锁死在某个材料或固定晶向；可提供常用预设，但保留通用输入。

如果用户必须先理解内部数组轴才能使用卡片，参数设计通常还不够好。

## 4. 设计控件和信息层级

- 首屏只放决定主要结果的常用参数。
- 把低频但仍面向用户的参数放入命名明确的高级区域。
- 模式切换后，无效控件应隐藏或禁用，并在旁边说明生效条件。
- 参数顺序遵循用户决策顺序，不照抄 dataclass 字段顺序。
- 单位紧邻输入框；范围或禁用语义放在简短 tooltip/说明中。
- 输出数量可能膨胀时，显示输入数、理论输出数、上限和实际首轮预览。
- 预览若随数据规模增长，按 `test-rigor-checklist.md` 的异步规则处理，不能让参数变化卡住主线程。

## 5. 检查文案、查找与翻译

每张卡片至少提供三层信息：

1. 卡片名称：短、可区分。
2. 查找卡片弹窗中的一句简述：说明“输入 → 操作 → 输出”，不要只重复名称。
3. 卡片文档：原理、参数、限制、示例和验证方法。

同时检查：

- `Find card` 的简述能否区分相似卡片；
- `Add new card` 下拉框、分组名、卡片名、模式枚举和新提示是否全部进入翻译目录；
- 中文是否自然，是否残留类名、内部 key 或未经解释的缩写；
- tooltip 是否补充限制，而不是代替必要的常驻说明；
- 错误信息是否指出哪个参数、哪项输入前提和可执行的修正方向。

## 6. 检查文档与界面是否同一设计

逐项对照 Params、UI、文档和序列化：

- 名称、默认值、单位、范围、枚举选项一致；
- 隐藏/禁用条件在文档中明确；
- 文档不声称代码没有实现的自动识别、任意取向、物理修复或 fallback；
- 示例使用真实可行的参数组合；
- 旧工作流行为改变时，写迁移说明，不用新默认值静默改写旧 JSON。

## 7. 输出审查结论

逐卡审查时，先给用户一个短表：

| 发现 | 用户影响 | 建议 | 是否改变旧行为 |
|---|---|---|---|

拿不准且会改变物理语义、默认值或旧工作流时再询问；纯文案、无歧义控件联动、缺失翻译和明显死参数可直接修复。

## 设计准入清单

- [ ] 一句话能说明输入、操作、输出和边界
- [ ] 与相邻卡片没有无法解释的功能重复
- [ ] 每个参数都有用户问题、可见效果、单位/参考系和测试
- [ ] 默认值、范围、精度和禁用语义合理
- [ ] 方向参数区分笛卡尔、晶格、晶面和局部参考系
- [ ] 参数联动不会留下“可编辑但不生效”的控件
- [ ] 查找弹窗有一句简述，新增入口和枚举均已翻译
- [ ] 文档与 UI/Params/序列化完全一致
